1. HEADLINE: "THE SERVER STARTED" IS NOT VERIFICATION

  The first check run was `streamlit run src/app.py` plus a curl for HTTP 200.
  It passed and proved almost nothing: Streamlit serves a static HTML shell
  regardless of whether the script works, and the script only executes when a
  browser session connects. A 200 here is compatible with a completely broken
  app.

  Verification therefore used streamlit.testing.v1.AppTest, which runs the real
  script in-process and exposes the rendered element tree. That is what made
  the three bugs in section 2 findable at all -- every one of them produced a
  page that started fine and rendered wrong.


2. THREE BUGS, NONE VISIBLE FROM A SERVER-HEALTH CHECK

  2.1  THE SIDEBAR NEVER RENDERED ON THE NORMAL PATH

    _render_sidebar() was called only inside the `if not index_ready:` branch,
    on the reasonable reading that an empty index means there is nothing to
    describe. So with a healthy index -- the state the demo actually runs in --
    the sidebar was absent: no corpus scope, no settings, no Clear chat, no
    second copy of the disclaimer.

    The server was healthy throughout. The page was missing half its content.

    Fixed by rendering the sidebar first, unconditionally, and keeping the early
    return for the empty-index case.

  2.2  st.text() TAKES ONE ARGUMENT, AND THIS RAISED ON EVERY RENDER

        st.text("Last indexed", ingested_at)     ->  TypeError

    with a 3-positional-arg signature. Every render of the sidebar raised, so the
    page showed an error instead of the app. Caught immediately by
    test_page_renders_with_no_exception once the sidebar was actually reached.

    Fixed with f-strings. This is the sort of thing a "does it start" check
    misses completely.

  2.3  `streamlit run` DOES NOT PUT THE PROJECT ROOT ON sys.path

    The app died on import with `ModuleNotFoundError: No module named 'src'`.
    `streamlit run src/app.py` puts src/ on the path, not the repo root, so
    `from src.config import CONFIG` cannot resolve. The CLI never hit this
    because `python -m src.cli` already places the root on the path.

    Fixed with an explicit PROJECT_ROOT sys.path insert at the top of app.py,
    before the src imports, with a comment saying why the CLI does not need it.

  A fourth, smaller one: tests/test_app.py resolved "src/app.py" relative to the
  process cwd, which pytest does not guarantee to be the repo root. Every test
  errored with FileNotFoundError until the path was anchored to the test file.

  Renders and calls. Zero business logic, which is the spec's hard constraint
  and the one that decays fastest as a project grows: every decision about what

  Layout, in the order implementation.md 4 specifies:

  Caching: chain.py memoises the Retriever and Generator in module globals, and

  first load takes a few seconds and is the only noticeable delay.


4. THE EMPTY-INDEX GUARD (A-RELEVANT, AND EASY TO GET WRONG)

  The spec asks for a guard showing "Run: python -m src.cli ingest" instead of a
  broken chat box. Two details matter:

  - It must not import sentence_transformers just to decide. Calling
    Retriever() to check would load the whole model on a page that is about to
    tell the user to go and build an index. It calls open_collection().count()
    and swallows any exception, which treats an unreadable store as "not ready"
    -- the right default, because the recovery instruction is the same.

  - The sidebar still renders on this path. Someone who has not ingested yet
    still benefits from knowing what the corpus is meant to contain. This was
    the direct cause of bug 2.1.

  NOTE THE INVERSION: this project ships with a built index, so the normal path
  is the one that matters for the demo. A guard that only works when the index
  is missing is not a guard.


5. WHY CHIPS USE A pending SLOT INSTEAD OF SENDING DIRECTLY

  A naive chip handler appends the question and renders the answer in the same
  run. If anything triggers a rerun before the assistant turn is drawn --
  and a button click is a rerun -- the question is appended twice and answered
  twice, so the transcript shows a duplicate.

  The pattern used here:

      chip click -> st.session_state["pending"] = question; st.rerun()
      next run   -> question = pop("pending") or chat_input value
                    pop, not get: it must be consumed exactly once

  Tested for all three chips: test_each_example_button_sends_its_question is
  parametrised over indices 0, 1, 2 and asserts exactly two chat messages, one
  user and one assistant. A duplicate would make it three.


6. src/app.py CALLS chain.answer() AND RENDERS. NOTHING ELSE.

  Verified by inspection rather than assertion, since it is a design rule rather
  than a behaviour: the only business entry point in the file is

      def _get_answered(question):
          from src.rag.chain import answer
          return answer(question)

  and it is called in exactly one place. There is no `if "expense ratio" in
  question` anywhere in app.py, which is the failure mode the spec warns about.

  The retrieval-gate constants are displayed but never re-implemented:
  MIN_SIMILARITY and MIN_LEXICAL_COVERAGE are read from CONFIG, so the sidebar
  cannot quote a number the retriever is not actually using.


7. THE DEBUG PANEL, WHICH IS THE POINT OF THE WHOLE PHASE

  "The single most valuable thing to show in a demo: it makes retrieval
  visible." Per hit: rank, score, scheme, section, raw unprefixed text, and the
  source URL.

  Note it shows `hit.chunk.text` -- the unprefixed text. The scheme and section
  prefix exists only in embedding_text(), so what the panel shows is precisely
  what a human can go and verify on the page. Showing the prefixed form would
  misrepresent what was stored.

  Rendering is gated on result.hits being non-empty, so a refusal that happened
  before retrieval shows no panel rather than an empty one, while a refusal
  AFTER retrieval (a generation failure) still shows the chunks that were read.
  That second case is why Answer.hits is populated on refusals, and it is what
  makes a no-key run debuggable rather than opaque.

  Verified live offline: 4 chunks, scores, and all 4 groww.in URLs rendered.


8. A HONEST LIMITATION OF THE VERIFICATION

  Everything in this document was verified WITHOUT a working answer layer,
  because no ANTHROPIC_API_KEY is available. So what was actually exercised is:

    - the guard refusals, which need no API call
    - the no-match refusal, which needs no API call
    - the retrieval + debug panel, up to the point of generation
    - every rendering path, layout, sidebar, expander, clear chat

  What was NOT exercised is a single generated answer rendered in the UI: no
  citation link, no <=3-sentence answer, no A2-style number, and no
  determinism check through the UI. Those are all covered by
  tests/test_acceptance.py, which is where the key is needed.

  Concretely, in every verified run the assistant bubble read "I couldn't find
  that on the HDFC source pages I have" -- because generation failed without a
  key, and chain.answer() correctly fell back to NO_MATCH. That is the
  no-traceback fallback working, but it is not a demonstration of the answer
  path. Anyone reading the transcripts of these runs should not mistake it for
  the retrieval gate refusing; the guard log says which it was.
